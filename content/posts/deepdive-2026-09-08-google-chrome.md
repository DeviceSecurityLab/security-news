## 30秒サマリ

- 2026年4月、Chrome のゼロデイ **CVE-2026-5281** に緊急パッチ。Microsoft の SharePoint ゼロデイと同週で、企業の"入口"が同時に狙われた。
- 5月、インフォスティーラー **VoidStealer** が Chrome の **App-Bound Encryption (ABE)** を回避する新手法を確立。ブラウザ保存の認証情報・クッキーが再び危険域に。
- 5〜8月にかけて Chrome のパッチ規模が異常に膨張（148で151件 → 382件 → 151で370件 → 152で300件超）。報道によればこの多くは **Google が AI を活用して発見**したもの。
- 8月、Google は**ポリシーインストール拡張機能による New Tab / 既定検索エンジンの乗っ取りをデフォルトでブロック**する機能を準備中と報じられた。
- 実務上の要点は3つ — ①更新の遅延をゼロにする ②ブラウザに認証情報を貯めない ③拡張機能の配布ポリシーを棚卸しする。

## 背景 — 何者か / 何が起きているか

今回の主役は攻撃者グループではなく、**製品そのもの**です。Google Chrome は世界で最も広く使われる Web ブラウザであり、記事でも「ブラウザは攻撃の最前線」と繰り返し指摘されています。つまり Chrome は、単なるアプリケーションではなく、**企業ネットワークの実質的な境界**として扱う必要がある、という前提から話を始めます。

2026年4月中旬から9月初旬にかけての約5か月間、Chrome まわりのニュースは大きく3つの層に分かれます。

1. **悪用済みゼロデイへの緊急対応**（4月）
2. **パッチ規模の爆発的な増加**（5月〜8月、AI による脆弱性発見が寄与）
3. **ブラウザ本体の穴ではなく、"周辺"を狙う攻撃への対抗**（ABE 回避、拡張機能ハイジャック対策）

この3層目が今回いちばん重要です。ブラウザ本体のメモリ安全性バグはベンダー側が高速に潰し続けている一方で、攻撃者は **すでにブラウザの中にある資産（保存パスワード、セッションクッキー）** と **正規の拡張機能配布ルート** に軸足を移している。この非対称性が、5か月分の記事を並べて初めて見えてきます。

なお、本テーマの別表記には「108件の悪意ある拡張機能」「Chrome 149未満」といったラベルが含まれますが、**今回参照した記事セットにはその詳細を記述した記事が含まれていません**。該当事案の具体的内容については、本台本では扱わず「報道時点では本データ内で未確認」として保留します。

## 時系列 — インシデントの連鎖

### 2026-04-15 ｜ ゼロデイ、しかも"横並び"で

Krebs on Security が報じた4月の Patch Tuesday は、Microsoft だけで **167件**。SharePoint Server のゼロデイ **CVE-2026-32201**（スプーフィングとして悪用中）、Windows Defender の権限昇格「BlueHammer」**CVE-2026-33825**（公開済み）、SQL Server の RCE **CVE-2026-33120** が並びました。

ここで注目すべきは、同じタイミングで **Adobe Reader の RCE（CVE-2026-34621、2025年から悪用）** と **Chrome のゼロデイ（CVE-2026-5281）** の緊急パッチが提供されたことです。

つまりこの週、攻撃者が現在進行形で悪用していたのは、**サーバ製品（SharePoint）とクライアント側の文書・Web 閲覧経路（Reader、Chrome）**の両方でした。初期侵入の入口が上下から同時に攻められている構図です。CVE-2026-5281 の技術的な詳細（脆弱性クラスや攻撃キャンペーンの帰属）は、本記事データ内では明らかにされていません。

### 2026-05-07 ｜ 防御機能そのものが回避される

Dark Reading が、**VoidStealer** の作者による **App-Bound Encryption (ABE) の新たな回避手法**を報道。

ABE は、そもそもインフォスティーラーによる Chrome 保存データの窃取を封じるために Google が導入した防御機構です。その回避手法が確立されたということは、**「Chrome を最新に保っていれば認証情報は安全」という前提が崩れた**ことを意味します。記事の深刻度評価自体は LOW ですが、実務的インパクトはここが一番大きい。

見出しが "**Yet Another** Way"（またしても別の方法）である点も見逃せません。ABE 回避は単発の事故ではなく、**継続的ないたちごっこ**として定着しつつある、という文脈がここに含まれています。

### 2026-05-30 ｜ Chrome 148、151件

リモートコード実行につながりうる重大な欠陥を含む **151件**を一括修正。この時点では「大規模アップデートだな」で済む数字でした。

### 2026-07-02 ｜ 382件 — 桁が変わる

SecurityWeek が「Google Patches 382 Chrome Vulnerabilities」を報道。うち **Critical 15件、High 67件**。1か月前の151件からさらに倍以上です。記事自身が「異例の多数」と表現しています。

### 2026-07-21 ｜ Chrome 150、use-after-free 6件

一転して、**Critical / High の use-after-free 6件**にフォーカスしたアップデート。メモリ安全性バグは RCE に直結しやすいクラスであり、件数は少なくても優先度は高い。

ここで**運用上の教訓**が一つ。「382件」の月と「6件」の月では、**件数と危険度が全く比例しない**。件数の多寡でパッチ適用の優先度を判断してはいけない、という実例です。

### 2026-07-31 ｜ Chrome 151、370件（Critical 7件）

Infosecurity Magazine の記事で、**370件のパッチ、うちクリティカル7件**。そしてここで明示されたのが「**AI による脆弱性発見の成果が反映されている**」という点です。

### 2026-08-03 ｜ 守りを"拡張機能"側に広げる

BleepingComputer が、Chrome に **ポリシーインストールされた拡張機能による New Tab ページ乗っ取り・既定検索エンジン改変をブロックする機能**が準備中と報道。デフォルト有効になる見込みとされています。

ブラウザハイジャッカーは「長年にわたりユーザー体験を損ない、マルウェア配布の経路となってきた」と記事は指摘します。注目すべきは対象が **ポリシーインストール（=管理者権限で強制導入される経路）** である点。攻撃者が正規の管理チャネルを悪用してくる現実に、ブラウザ側が対処し始めたということです。

### 2026-08-27 ｜ Chrome 152、300件超

再び **300件超**。記事は「多くは Google が AI を活用して発見したもの」としつつ、「**研究者による高価値な Chrome 脆弱性の発見も続いている**」と付記しています。AI がスケールで薄く広く掘り、人間の研究者が深く難しいものを掘る、という**役割分担が明確に見え始めた**のがこの時点です。

---

**流れとして読むと** — 4月にゼロデイ悪用という「実害フェーズ」があり、5月以降は Google が AI を投入してバグを産業的に刈り取る「体力勝負フェーズ」に入った。同時に攻撃者は、潰されにくい領域（保存済み認証情報の窃取、拡張機能の配布経路）へシフトした。8月の拡張機能ブロック機能は、その攻撃者シフトに対する Google 側の追随と読めます。

## 手口・技術詳細 (TTP)

**1. ブラウザ本体のメモリ破壊系（Initial Access / Execution）**

- **use-after-free**（Chrome 150 で6件修正）。解放済みメモリへの参照を悪用してコード実行に至るクラスで、記事は「リモートコード実行に悪用される可能性が高い」と評価。
- Chrome 148 / 382件パッチ / Chrome 151 / 152 でも、リモートコード実行につながりうる Critical・High 級が継続的に修正されています。
- ゼロデイ **CVE-2026-5281** は積極悪用が確認された事例。具体の悪用手法は本記事データでは未記載。

**2. App-Bound Encryption (ABE) の回避（Credential Access）**

- Chrome は保存済み認証情報・クッキーを ABE で保護しますが、**VoidStealer** がこれを回避する手法を確立。
- 結果として、**インフォスティーラーが Chrome 内の認証情報とクッキーを取得できる経路**が再び開通。クッキーが取れるということは、**MFA を通過済みのセッションをそのまま奪える**ということです（※記事はクッキー取得までを記載。セッションハイジャックへの発展はその論理的帰結であり、具体的な被害報告は本データ内では未確認）。

**3. 拡張機能によるブラウザハイジャック（Persistence / Defense Evasion）**

- New Tab ページの乗っ取り、既定検索エンジンの改変。
- 経路は **ポリシーインストールされた拡張機能** — つまり、ユーザーが手動で入れたものではなく、管理ポリシー経由で配られたものが悪用され得る。
- 記事はこれを「マルウェア配布の経路」と明記しています。

**4. 攻撃タイミングの同期（横断的観点）**

- 4月の事例では SharePoint（サーバ）・Adobe Reader（文書）・Chrome（Web）に同時期のゼロデイ／悪用済み脆弱性が集中。単一製品の防御では足りないことを示しています。

## 影響と被害範囲

| 対象 | 影響 |
|---|---|
| Chrome を使う全ユーザー | パッチ未適用ならリモートコード実行等のリスクに晒される（148 / 150 / 151 / 152 各記事） |
| Chrome に認証情報を保存している環境 | ABE 回避により認証情報・クッキーが窃取され得る。企業端末で特に深刻 |
| ポリシーで拡張機能を配布している組織 | New Tab 乗っ取り・検索エンジン改変の対象。ブロック機能展開後は**正規の業務用拡張機能が動かなくなる可能性**もある |
| SharePoint Server を公開している組織 | CVE-2026-32201 が悪用中（4月時点） |
| SQL Server / Adobe Reader 利用環境 | それぞれ RCE リスク。Reader の CVE-2026-34621 は 2025年から悪用 |

被害の具体的な件数・被害組織名・金銭的損失については、**本記事データ内には記載がなく未確認**です。

## 防御・推奨アクション

**優先度 1 — 今日中（悪用確認済みへの対応）**

1. **Chrome を最新版へ**。観測期間中に確認された最新は **Chrome 152**。管理下の全エンドポイントで実バージョンを棚卸しし、「自動更新が有効になっている」ではなく「**実際に更新済みである**」ことを確認する。ブラウザは再起動するまで更新が完了しない点に注意。
2. **CVE-2026-5281（Chrome）と CVE-2026-32201（SharePoint）を最優先で適用**。4月時点で積極悪用が確認されています。
3. Adobe Reader（CVE-2026-34621）、Windows Defender（CVE-2026-33825）、SQL Server（CVE-2026-33120）も同一サイクルで処理する。

**優先度 2 — 今週中（認証情報の防衛）**

4. **ブラウザへの認証情報保存を最小化**し、エンタープライズ向けパスワードマネージャーへ移行する。ABE が回避可能である以上、「ブラウザに預ける」こと自体がリスク受容になります。
5. **エンドポイント保護製品のインフォスティーラー検知ルールを最新化**する（VoidStealer 系を含む）。
6. Chrome のパスワード保存機能を **エンタープライズポリシーで無効化**することを検討する。

**優先度 3 — 今月中（構造的な対策）**

7. **ポリシーインストールされた拡張機能の全棚卸し**。何が、誰の承認で、どの権限で配られているか。8月報道のブロック機能がデフォルト有効になると、**乗っ取り系の挙動を持つ拡張機能が停止する**ため、事前に業務影響を洗い出しておく。
8. 拡張機能は**許可リスト方式**（ExtensionInstallAllowlist / ForceList）に寄せ、任意インストールを止める。
9. **件数でパッチ優先度を判断しない**運用ルールを明文化する。Chrome 150 の「6件」は Chrome 151 の「370件」より緊急度が高い局面があり得ます。判断軸は件数ではなく、**悪用の有無 → 脆弱性クラス（UAF 等 RCE 直結型） → Critical 件数**の順。

## 今後の見通し

**1. パッチ件数のインフレは続く可能性が高い。**
Chrome 151・152 の報道が示すとおり、Google は AI による脆弱性発見を本格導入しています。今後「1リリースで数百件」は例外ではなく常態になると見るのが自然です。これは**運用側の意味を変えます** — リリースノートを人力で読み込んで優先度を判断する運用はスケールしません。「最新版に上げ切っているか」という**バージョン統制の一点管理**に切り替えるべきです。

**2. 攻撃の重心はさらに"ブラウザの外側"へ。**
本体の脆弱性が AI で機械的に潰されるほど、攻撃者にとってエクスプロイト開発の費用対効果は下がります。相対的に旨みが増すのが、ABE 回避のような**保存済み資産の窃取**と、拡張機能のような**正規経路の悪用**です。5〜8月の記事の並びは、まさにその移行を示しています。

**3. 拡張機能まわりの規制強化。**
8月報道の New Tab 乗っ取りブロックはあくまで「準備中」段階で、**正式リリース時期・最終仕様は報道時点では未確定**です。ただし方向性としては、拡張機能に対する Chrome 側の制約は今後も強まると予想されます。管理者は「ポリシーで押し込めば何でも通る」前提を捨てておくべきです。

**4. 研究者による高価値バグは残り続ける。**
Chrome 152 の記事が明示するとおり、AI が広く浅く掘っても、**人間の研究者による高価値な発見は継続**しています。ゼロデイが枯れることはなく、CVE-2026-5281 のような事案は再発すると想定した運用（=緊急パッチを24時間以内に流せる体制）が必要です。
